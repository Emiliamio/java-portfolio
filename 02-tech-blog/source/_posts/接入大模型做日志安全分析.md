## 项目背景

做完日志审计系统和日志解析工具之后，我开始思考一个问题：**能不能让 AI 来帮我判断一条日志有没有安全风险？**

传统做法是写规则——IF 含有 "SQL injection" THEN 标记为高危。但规则总有漏洞：攻击者稍微换个写法就绕过去了。大语言模型恰好擅长这种模式识别。

于是有了这个项目：**日志智能分析助手 (Nexus AI)**。

它不是训练或微调模型，而是把大模型 API 集成到业务流程里——恰好是 JD 上"了解大模型工程化应用"这条要求想要的能力。

## 核心功能

| 功能 | 说明 |
|------|------|
| AI 日志分析 | 调用大模型 API，分析日志的安全风险和操作类型 |
| 风险评估 | 五级：NORMAL / LOW / MEDIUM / HIGH / CRITICAL |
| 智能建议 | AI 自动生成中文处置方案 |
| 降级保护 | LLM 输出异常时，自动切换关键词规则引擎 |
| 分析历史 | 每次结果存入 MySQL，支持回顾 |
| 快捷示例 | 内置 5 种典型日志场景 |

## System Prompt 工程

这是这个项目最有技术含量的部分。我没有直接把日志丢给模型问"有没有风险"，而是构造了一个结构化的 System Prompt：

```java
private String buildSystemPrompt() {
    return """
        你是一个专业的日志安全分析专家。用户会给你一段系统日志，请你分析后
        严格按照以下 JSON 格式返回结果（只返回 JSON，不要包含任何其他文字）：

        {
          "operationType": "操作类型，如 LOGIN/QUERY/DELETE/UNKNOWN",
          "riskLevel": "风险等级：NORMAL / LOW / MEDIUM / HIGH / CRITICAL",
          "needIntervention": true或false,
          "suggestion": "处置建议，中文，50字以内",
          "summary": "一句话摘要描述这条日志在做什么，中文，30字以内",
          "sourceIp": "日志中的源IP地址，没有则为null"
        }

        风险等级判断标准：
        - NORMAL: 正常操作
        - LOW: 轻微异常（如偶尔的密码错误）
        - MEDIUM: 需要关注（如连续失败、权限不足）
        - HIGH: 严重威胁（如暴力破解、未授权访问）
        - CRITICAL: 紧急事件（如SQL注入、XSS、路径遍历）
        """;
}
```

面试时会问的关键点：
- **为什么用 System Prompt 而不是 User Prompt？** → System Prompt 设定持久角色和规则，User Prompt 是具体输入。把判定标准放在 System Prompt 中，模型在整个对话中始终遵循
- **为什么要求只返回 JSON？** → 避免 markdown 代码块包装，减少解析失败的概率
- **为什么在 Prompt 里写风险标准？** → Few-shot 思想——给模型明确的判断框架，比让它自由发挥更可控

## 降级策略

大模型 API 可能返回格式异常——多了自然语言前缀、JSON 被 markdown 包裹等等。我设计了降级规则引擎：

```java
// 当 LLM 返回无法解析时，自动切换关键词规则
private AnalysisResult fallbackAnalysis(String rawText) {
    if (upper.contains("SQL INJECTION") || upper.contains("' OR '1'='1")) {
        result.setRiskLevel("CRITICAL");
        result.setNeedIntervention(true);
        result.setSuggestion("检测到 SQL 注入攻击特征");
    } else if (upper.contains("<SCRIPT>") || upper.contains("XSS")) {
        result.setRiskLevel("CRITICAL");
        // ...
    }
    // 更多规则...
}
```

**面试要点**：降级策略体现的是**高可用性设计**——大模型不可靠时，系统依然能给出有意义的分析，不会直接崩溃。

## API 格式自适应

`buildRequestBody()` 通过判断 API URL 是否含 `"anthropic"` 自动切换请求体格式：

- Anthropic Messages API：`system` 顶层字段 + `content[]` 数组
- OpenAI Chat Completions：`messages[]` 中包含 system role

**面试要点**：不锁定单一供应商，改一下配置就能换模型，代码零改动。

## JDK HttpClient 的选择

我没有用 Spring 的 RestTemplate 或 WebClient，而是用 JDK 11+ 内置的 `java.net.http.HttpClient`：

```java
HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create(apiUrl))
    .header("x-api-key", apiKey)
    .timeout(Duration.ofSeconds(timeoutSeconds))
    .POST(HttpRequest.BodyPublishers.ofString(requestBody))
    .build();
```

理由：零外部依赖，支持 async、HTTP/2、超时控制。面试时可以讲"我知道 RestTemplate 和 WebClient，但这里故意用更轻的方案"。

## 安全性设计

- **API Key 用 `System.getenv("AI_API_KEY")` 读取**，绝对不写在代码或配置文件里
- **输入校验**：`@Valid` + `@Size(min=5, max=5000)` 防恶意输入
- **响应不泄露内部异常**：`GlobalExceptionHandler` 对客户端返回友好信息
- **前端 XSS 防护**：`escapeHtml()` 处理所有用户可见的历史日志

## 测试

8 个 JUnit 5 测试覆盖核心逻辑：

| 测试场景 | 验证点 |
|----------|--------|
| 正常 JSON 解析 | operationType / riskLevel / needIntervention 全部正确提取 |
| JSON 被 markdown 包裹 | 容错提取 `{...}` 块 |
| SQL 注入降级 | "SQL injection: ' OR '1'='1" → CRITICAL |
| XSS 降级 | "<script>alert(1)</script>" → CRITICAL |
| 路径遍历降级 | "../" → HIGH |
| 单次登录失败降级 | "LOGIN FAIL wrong password" → LOW |
| 未授权访问降级 | "Unauthorized access" → MEDIUM |
| 缺失字段 JSON | 默认值填充正确 |

## 前端设计

采用了暖灰 + 米白的研究员工作台风——输入框在左、历史列表在右的分栏布局。快捷示例按钮覆盖了暴力破解、SQL 注入、XSS、路径遍历、正常操作、未授权访问六种场景，面试时一键填充，无需手动复制粘贴。

## 面试能聊的点

1. **"你是怎么调大模型 API 的？"** → System Prompt 设定角色 + JSON 输出约束 + 降级规则引擎
2. **"如果 LLM 返回不稳定怎么办？"** → 降级策略，关键词规则兜底，保证可用性
3. **"为什么不锁定一个模型供应商？"** → 通过 URL 判断自动适配 Anthropic / OpenAI 两种格式
4. **"API Key 怎么管理的？"** → `System.getenv()` 读取，`.env` 不提交 Git，`.env.example` 提供模板
5. **"这个项目和前面项目的关联？"** → 项目二的解析结果可以粘贴到项目三做 AI 深度分析，项目一的查询结果也能导入分析
